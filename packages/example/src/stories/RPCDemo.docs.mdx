# `RPC` 文档和演示

## 介绍

`@event-chat/rpc` 存在最大的意义在于，抹平了通信方式，让开发者从不同类型对象的收发消息中释放出来；转而只需要编写 `service` 上下文中来，更关注实际业务本身。

- 纯浏览器客户端 `RPC` 库，支持：`iframe`、`web worker`、`service worker`、`messagePort`、`shared worker`、`webSocket` (client)
- 提供心跳检测、消息发送、广播、多播，跨域、跨 `Window`、跨线程通信
- 开箱即用，提供 “上下文“ 即可通信，自动推导请求方法的参数类型和返回类型
- `Tree Shaking` 模式，根据通信的类型划分模块

## 安装

```shell
# npm
npm install @event-chat/rpc

# yarn
yarn add @event-chat/rpc

# pnpm
pnpm add @event-chat/rpc
```

## 快速上手

`@event-chat/rpc` 内部根据不同类型的通信已做了处理，业务使用时仅需提供上下文用于通信

```typescript
const parentCtx = createCtx(
  () => ({
    sendMessage: (msg: string) => {}, // 消息请求方法
  }),
  () => ({
    brodcast: () => {}, // 广播
  })
)

const iframeCtx = createCtx(() => ({
  sendMessage: (msg: string) => {},
}))
```

`Window` 父级绑定自身和消费方上下文、驱动函数、通信对象（和 `iframe` 通信还需要提供允许的 `origin`）

```typescript
const ParentCom: FC = () => {
  const iframeRef = useRef<HTMLIFrameElement>(null);
  const { connected, rpc } = useRPC({
    config: { allowedOrigins: ["*"], channel: "window-group" },
    brodcast: parentCtx.brodcasts,
    consume: iframeCtx.actions,
    event: parentCtx.actions,
    drive: createWindowRPC,
    init: () => iframeRef.current,
  });

  return (
    <>
      <iframe ref={iframeRef} src="/demo" />
      <button
        disabled={connected}
        type="button"
        onClick={() => {
          rpc.request("sendMessage", { payload: "test-demo" }).catch(() => {});
        }}
      >
        click it
      </button>
    </>
  );
};
```

`iframe` 绑定自身和消费方上下文、驱动函数、通信对象

```typescript
const IframeCom: FC = () => {
  const { connected, rpc } = useRPC({
    config: { allowedOrigins: ["*"], channel: "window-group" },
    consume: parentCtx.actions,
    event: iframeCtx.actions,
    drive: createWindowRPC,
    init: () => window.parent,
  });

  return (
    <>
      <button
        disabled={connected}
        type="button"
        onClick={() => {
          // 发送消息
          rpc.request("sendMessage", { payload: "test-demo" }).catch(() => {});
        }}
      >
        click it
      </button>
      <button
        disabled={connected}
        type="button"
        onClick={() => {
          // 广播
          rpc.broadcast({ payload: "test-broadcast" });
        }}
      >
        brodcast
      </button>
    </>
  );
};
```

### 提供上下文

**创建上下文：**

创建上下文有 2 个方法：`createCtx` 以及该函数的包装方法 `createService`，使用方式和返回结果都一致，区别在于上下文类型定义位置不同：

```typescript
// 接受 2 个函数作为参数，第一个函数返回请求的方法集合，第二个函数返回广播的方法集合
const messageEvent = createService<DemoCtxType>()
const iframeCtx = messageEvent(
  (ctx) => ({
    sendMessage: (msg: string) => ctx.print?.(msg),
  }),
  (ctx) => ({
    brodcast: (msg) => ctx.print?.(String(msg)),
  })
)

// 使用时上下文的属性必须为可选类型
const parentCtx = createCtx(
  (ctx: Partial<DemoCtxType>) => {
    sendMessage: (msg: string) => ctx.print?.(msg)
  },
  (ctx: Partial<DemoCtxType>) => ({
    brodcast: (msg) => ctx.print?.(String(msg)),
  })
)

interface DemoCtxType {
  print: (msg: string) => void
}
```

更多上下文示例见 `Github` [[仓库源码](https://github.com/event-chat/event-chat/tree/main/packages/example/src/services)]

**返回的上下文对象：**

创建上下文将会返回一个对象，提供给 <Tag>RPC</Tag> 实例使用，包含以下属性：

- `action`：作为 `event` 则作为当前实例的接收请求的方法，作为 `consume` 则作为实例发起请求的方法
- `brodcast`: 作为当前实例接收广播的方法
- `provider`: 为当前作用域上下文提供指定类型的对象

当提供 `action` 作为实例请求方法时，通过 `request` 发起的请求将自动匹配：方法名、所需参数、返回结果；以上可根据业务进行配置，不需要可忽略

**上下文作用域：**

由于主线程所有上下文共享一个作用域，因此在组件中存在不同的 <Tag>RPC</Tag> 实例时，需要生成不同的上下文作为当前实例方法：

```typescript
const messageEvent = createService<DemoCtxType>()
const generateCtx = () =>
  messageEvent(
    (ctx) => ({
      sendMessage: (msg: string) => ctx.print?.(msg),
    }),
    (ctx) => ({
      brodcast: (msg) => ctx.print?.(String(msg)),
    })
  )

const DemoCom: FC = () => {
  const iframeCtx = generateCtx()
  useRPC({
    brodcast: iframeCtx.brodcasts,
    event: iframeCtx.action,
    drive: createWindowRPC,
    init: () => window.parent,
  })

  iframeCtx.provider({ print: () => {} })
  return null
}

interface DemoCtxType {
  print: (msg: string) => void
}
```

补充：

- 独立的 `worker` 线程内部可以直接使用上下文；不同实例之间如果使用相同请求方法，而上下文需要不一样时，也可以动态创建上下文；
- 由于 `consume` 仅作为实例请求方法的类型推断，因此不需要考虑上下文作用域；

### `RPC` 实例方法

调用 `RPC` 实例方法前请先确定实例 `connected` 状态，以确保实例已完成初始化

#### `broadcast`

用于发起广播

```typescript
type broadcast = <T>(
  options?: Omit<RequestOptions<T>, 'retry'>,
  fallback?: (error: unknown) => void
) => MessageItem
```

- 参数 `options` 类型和 `request` 一致，但不支持失败重发
- 广播是同步函数，和 `request` 不同，不会将响应结果通过 `Promise` 返回
- 返回 `MessageItem` 类型的消息，用于获取 `requestId` 和 `sign` 转发广播

#### `config`

更新实例配置，除了调试方法之外的配置都允许更新

```typescript
type config = (options: Omit<RPCOptionsType, 'debug' | 'onConnect' | 'onDisconnect'>) => void
```

#### `connected`

获取实例 `connected` 状态

```typescript
type connected = () => void
```

#### `getType`

获取实例类型，用于作用域内批量广播时筛选类型

```typescript
type getType = () => string
```

#### `request`

请求方法根据提供的上下文，自动推断请求和响应的类型；使用 `BroadcastChannel` 创建的实例不支持 `request` 方法

```typescript
type request = <T = unknown>(type: PropertyKey, options?: RequestOptions<T>) => Promise<unknown>
```

`options` 的类型和配置：

```typescript
type IframeSerializeOptions = StructuredSerializeOptions & {
  targetOrigin?: string
  transmit?: () => Promise<readonly WindowClient[]>
}

type RequestOptions<T = unknown> = IframeSerializeOptions &
  Pick<MessageItem, 'requestId' | 'sign'> & {
    payload?: T
    retry?: number
  }
```

- `requestId`：请求 `id` 主要用于广播去重，`request` 会丢弃
- `sign`：请求的签名，和 `requestId` 一样
- `payload`：发送的消息，根据上下文推导类型
- `retry`：当前重复的次数
- `targetOrigin`: 匹配的源，仅用于跨域通信，默认为 `self?.location.origin`
- `transfer`: 从当前线程转移对象，如：`MessagePort`
- `transmit`：仅用于 `service worker` 匹配 `clients` 批量转发消息

#### `upset`

更新 `Transports` 对象的配置，用于监听 `message` 时，提供的第三个参数

```typescript
type upset = (options: FactoryOptions) => void
```

### 发起请求

实例通过 `request` 方法发起请求，请求的名称、所需的参数以及响应的类型，会根据提供的 `consume` 上下文自动推导，例如：

```typescript
rpc.request('connectWritableStream', { transfer: [payload], payload }).catch(() => {})
```

> 当提供 `consume` 上下文时，而通信的对象 `event` 没有绑定，发起请求不会得到响应，也不会报错

`rpc.broadcast` 匹配多个实例广播的情况：

- `BroadcastChannel`：对象本身就是为了向不同的标签页、`window` 对象相互通信
- `ServiceWorkerRegistration`：同链接同 `scope` 下的 `sw` 只允许存在一个 `active` 实例，为了保活每个实例，因此会借助 `active` 实例对象，为每个同 `scope` 的实例通信

为了避免广播不受控制，可以通过 `channel` 的方式限制广播范围

**广播转发：**

当转发广播时，有可能因消息回环导致无限循环。为避免这个情况，允许广播时携带：`requestId` 和 `sign`，内部会存储发送的签名进行匹配，已记录签名的广播不会在同一个实例重复接收

**`brodcastScope` 筛选实例广播**

在范围向所有挂载的实例发送广播时，提供的参数中有 4 个配置可筛选符合要求的实例发送广播

- `exclude`: 类型集合，不在集合范围的实例能够发起广播
- `include`: 类型集合，必须是集合范围的实例能够发起广播
- `scopein`: 名称集合，只有名称存在集合的实例能够发起广播
- `scopeout`:名称集合，名称不在集合的实例能够发起广播

集合类型为 `string[]`，实例的类型可以通过 `TARGET_TYPE_STRINGS` 获取；使用 `RPCProvider` 时，默认会在每个实例初始化后，自动挂载空字符作为实例的匿名名称，如果需要修改挂载的实例的名称，可以通过 `useRPC` 返回的函数 `mount`

### 实例的启动和注销

默认情况下实例初始化后会自动发起心跳，无论是否连接成功，都会保持心跳检测；同时会在 `hooks` 所在的组件注销前，注销实例，因此通常情况下不需要手动 `start` 或 `destroy`。但是 `service worker` 线程并非持久连接，会随浏览器空闲时临时关闭线程，对于这种情况：

- 通常由心跳唤醒 `service worker` 实例，一般不需要手动处理
- 但如果因为某些情况强制关闭了线程，例如调试工具强制卸载
- 这样的情况在 `onDisconnect` 回调函数中，提供参数 `destroy` 给业务判断当前实例是否已注销
- 对于已注销的实例可以调用 `start` 手动重新发起新的实例连接

其他情况不建议手动 `start` 或 `destroy`，除非你对实例生命周期非常了解

初始化实例的方式和 `web worker` 一致，但 `service worker` 有几个独有特性

#### 共享 `active` 实例

由于浏览器限制，同链接同 `scope` 共享 `active` 实例，因此：

- 发起广播时通过消息签名避免消息回环
- `request` 发送消息时，会将 `requestId` 挂载 `pending` 集合中，最终响应会匹配到正确的实例

#### 转发消息

发送请求时可以通过 `transmit` 返回多个 `clients` 用于转发消息给多个实例，如下：

```typescript
rpc
  .request('sendMessage', {
    payload: 'msg...',
    transmit: () =>
      self.clients.matchAll({
        type: 'window',
        includeUncontrolled: true,
      }),
  })
  .catch(() => {})
```

#### 慢请求

当 `service worker` 内部需要完成耗时的请求时，为了避免浏览器空闲时注销 `service worker` 线程，导致通信失败；实例内部通过 `waitUntil` 的方式等待请求完成，因此在 `sw` 内部上下文中，可以使用异步方法的 `await`，如下：

```typescript
const workerCtx = createCtx(() => ({
  sendMessage: async () => {
    const result = await fetch('...').then((res) => res.json())
    return result as ResultType
  },
}))
```

#### 唤起 `service worker`

`service worker` 除了通过 `message` 唤起线程外，还可以拦截 `fetch` 并唤起线程；在 `RPC` 实例内部，对这两种方式都做了监听，可以在拦截 `fetch` 的同时向主线程发起通信，如下：

```typescript
self.addEventListener('fetch', (event) => {
  if (event.request.url.includes('/api/hello')) {
    rpc.request('sendMessage', { payload: 'request start' }).catch(() => {})
  }
})
```

上述提到在主线程中 `service worker` 存在多个实例共享 `active` 通信的，在拦截 `fetch` 情况下向主线程发送消息，有可能多个实例都会响应。由于主线程此时是接收方，不存在和请求对应的 `pending`，不能明确接收对象，只能通过以下方式来区分：

- 每个实例的上下文采用不同的请求方法
- 由业务的消息自行决定如何处理
- 通过 `channel` 划分接收对象

**其他唤醒方式：**

除了 `fetch` 和 `message` 之外，`service worker` 还有诸如：`notice`、`sync` 等这样唤起方式；但只有 `fetch` 和 `message` 能够拿到明确的 `client`，其他唤起方式可以在发送请求时通过 `transmit` 匹配对应的 `clients`。

#### 观察共享实例

`SharedWorkerGlobalScope` 作为共享线程，内部的通信全部共享一个线程（参考主线程），每个通信通过 `MessagePort` 隔离通信。因此舍弃针对 `SharedWorkerGlobalScope` 建立 `RPC` 实例监听。而是使用方法 `obseverShareWorkerGlobalScopeRPC` 通过观察模式发起通信，如下：

```typrscript
const { brodcastScope } = obseverShareWorkerGlobalScopeRPC(target, () => {
  const workerCtx = generateWorkerCtx()
  return {
    context: {
      config: { channel: sharedGroup },
      brodcast: workerCtx.brodcasts,
      consume: mainConsume.actions,
      event: workerCtx.actions,
    },
    provider: ([rpc]) => {
    },
  }
})
```

观察方法配置的参数和驱动方法一致，第 2 个配置参数增加了 3 个可选属性：

- `destroy`：布尔型，设为 `true` 会在 `RPC` 断开后直接注销，并从观察队列中删除
- `name`：字符型，给观察的实例集合起个名字，广播时筛选用
- `provider`：为上下文提供需要的对象

内置 `provider` 的原因是 `SharedWorkerGlobalScope` 通过 `connect` 根据连接的情况，动态创建的 `MessagePort`。无法通过具体对象初始化实例，因此通过回调的方式，从观察方法中获取 `RPC` 实例，以便作为上下文所需的方法再次发起请求。

观察方法会返回一个 `brodcastScope` 方法，其用法和 `useRPC` 提供的同名方法一样。

#### 上下文

在 `SharedWorkerGlobalScope` 中由于多个主线程共享 1 个 `worker`，因此需要通过函数调用的方式隔离每个实例的上下文，如下：

```typescript
const messagePortEvent = createService<MessagePortCtx>()
export const generateWorkerCtx = () =>
  messagePortEvent(
    (ctx) => ({
      sendMessage: (data: RequestType) => {
        ctx.print?.(generateFakePrint(data, 'sharedWorker'), data)
      },
    }),
    (ctx) => ({
      brodcast: (info) => {
        const { data, success } = requestSchema.safeParse(info)
        if (success) ctx.print?.(generateFakePrint(data, 'sharedWorker-transmit'))
      },
    })
  )
```

在同一个 `sharedWorker` 中，由于共享一个线程，创建了多个 `RPC` 实例情况下，如果上下文的方法同名，可能会造成竞态请求；对此可以通过 `channel` 区分不同的实例。

#### 观察其他类型实例

`obseverShareWorkerGlobalScopeRPC` 是基于 `observerMessagePortRPC` 实现的，通过这个方法可以手动创建基于 `MessagePort` 的 `RPC` 实例，并将其添加到观察集合，如下：

```typescript
const { brodcastScope, push } = observerMessagePortRPC()
push(port, () => ({
  context: {},
  destroy: true,
  provider: ([rpc]) => {},
}))
```

`observerMessagePortRPC` 返回 2 个方法：

- `brodcastScope`：向观察的集合中，每个已连接的实例发送广播
- `push`：手动添加实例到观察集合

> 和 `obseverShareWorkerGlobalScopeRPC` 不同的是，手动添加实例可以针对单个实例去设置 `name`，用于筛选实例名称进行广播

无论是 `observerMessagePortRPC` 还是 `React` 中的 `PRCProvider` 都是基于 `observerRPC` 实现多实例广播，对于非 `MessagePort` 类型的 `RPC` 实例，可以自行手动添加观察集合，如下：

```typescript
const { brodcastScope, clear, push } = observerRPC()
push(port, {
  context: {},
  provider: ([rpc]) => {},
})
```

`observerRPC` 返回 4 个方法：

- `add`: 手动添加实例到观察集合
- `brodcastScope`: 向观察的集合中，每个已连接的实例发送广播
- `remove`: 手动删除观察集合中的实例
- `clear`：清空集合中的实例

相比较 `observerMessagePortRPC`，观察方法 `observerRPC` 更自由配置监控集合，因此没有扩展配置方法，需要初始化实例后自行添加到集合，如下：

```typescript
const { add, brodcastScope } = observerRPC()
const [RPCIns] = createMessagePortRPC(target, {
  context: {
    config: {
      onConnect: () => {
        add(RPCIns, 'custom-name')
      },
    },
  },
})
```

每调用一次观察方法将创建 1 个集合，通过 `brodcastScope` 发起广播时，会向集合中每个已连接的实例发送广播；可以根据业务创建不同的集合进行广播；可以将不同类型的实例添加到集合中，例如：`worker`、`Window`、`MessagePort`，也可以借助观察方法，扩展到诸如 `Vue` 这样的框架中。

#### 主线程中添加观察实例

在 `PRCProvider` 内的子组件中使用 `useRPC` 创建的实例，会在初始化后自动添加到观察集合中。而 `MessagePort` 需要手动创建实例，即便是在主线程中，是不会添加到 `RPCProvider` 的观察集合中，可以手动通过 `hooks` 返回的方法 `mount` 挂载实例。如下：

```typescript
const DemoCom: FC = () => {
  const { mount } = useContext(RPCInstanceContext);
  return (
    <button
      type="button"
      onClick={() => {
        const [rpc] = createMessagePortRPC(port);
        mount(rpc, "custom-port");
      }}
    >
      Add port
    </button>
  );
};
```

`mount` 方法也可以通过 `useRPC` 获取，从集合中删除实例只需空缺第二个参数即可，如：`mount(rpc);`，对于非 `React` 环境的情况，例如原生 `JS`，可以调用 `observerRPC` 将实例添加到观察集合中，上述已说明不再重复描述。

  ]}
  of={Transfer}
  sourceState="none"
/>

#### 发起转移

通过 `request` 或 `broadcast` 发起转移，转移的方式和 `postMessage` 一致

- `payload`：作为通信的信息，用于存放转移的对象，但 `MessagePort` 只能放在 `transfer` 中转移
- `transfer`：作为转移对象的集合，一次可以转移多个对象

```typescript
const messageChannel = new MessageChannel()
const payload = new ArrayBuffer(16)

rpc.request('sendMessage', { transfer: [messageChannel.port2, payload], payload }).catch(() => {})
```

由于 `transfer` 只允许转移一次，一旦成功转移对象将不允许再次转移，除非接收 `transfer` 的实例再次转发。因此配置了 `transfer` 对象，将无视请求配置 `retry` 次数，如果需要可以通过 `retryTimeout` 延长请求过期时间。

#### 接收转移

在上下文中获取转移的对象：

- `MessagePort` 在上下文的方法中第二个参数，获取对象属性 `ports` 进行筛选筛选
- 其他类型转移的对象可以直接定义在接收的消息类型中

```typescript
const workerCtx = createCtx(() => ({
  sendMessage: (buff: ArrayBuff, info) => {
    const { ports } = info ?? {}
    ports.filter((item) => item instanceof MessagePort)
  },
}))
```

不同的 `transfer` 对象，可能由于转移对象生命周期等问题，造成转移失败。对于这种情况：

- `request` 请求会通过 `Promise.reject` 抛出异常
- `broadcast` 接受一个参数方法 `fallback` 作为异常捕获的回调函数。

虽然对象只能转移一次，而作为广播可能会向多个实例进行通信，但仍旧保留了 `broadcast` 通过 `transfer` 转移对象的能力；因为接受广播的数量由业务决定，在允许的情况下确实可以用于转移对象，但不建议这样使用。

由于目前 `RPC` 实例托管的对象全部来自客户端，所以目前 `WebSocket` 也只提供了客户端支持；服务端部分待根据后续实际需求，再来评估如何完善。

向服务端发送的请求支持 3 个类型：`string`，`ArrayBuffer`，`Blob`，为了类型统一消息类型，目前将数据通过 `JSON.strify` 转换成 `string` 再发送到服务端，也会将收到的服务端数据通过 `JSON.parse` 转换成对象。也就是说暂且不支持收发 `ArrayBuffer` 和 `Blob` 类型的消息，如果需要可以通过上下文的方式手动发送

```typescript
const socket = new WebSocket('...')
useRPC({
  event: webSocketCtx.action,
  drive: createWebSocketRPC,
  init: () => socket,
})

// 手动发送 ArrayBuff
webSocketCtx.provider({ print: (buff: ArrayBuff) => socket.send(buff) })

// 手动监听消息
socket.onmessage((event) => {
  if (event.data instanceof ArrayBuff) {
    new Uint8Array(event.data)
  }
})
```

`rpc` 实例内部监听消息为了和外部做区分，通过消息中是否携带 `__RPC__` 属性值做判断
